O PEDIDO

O que queremos desta sessão

Não é uma apresentação de venda. É uma revisão de projeto com quem conhece a plataforma por dentro.

Atacar as escolhas

Cinco decisões estruturais estão registradas em ADR e são caras de reverter depois da Onda 2. Queremos saber quais delas o time do Google desfaria — e com que argumento.

Apontar o serviço melhor

O custo de infra é do cliente. Queremos crítica sobre particionamento, retenção, slots vs. on-demand e o que quebra quando o ONS semi-horário entrar.

Nenhuma linha chegou a um BigQuery real — o projeto GCP do cliente ainda não foi provisionado. É o melhor momento possível para uma crítica: nada está gasto, nada está migrado.

ness.05 · Origem

CONTRATO DE DADOS

Como tratamos fonte sem contrato estável

CCEE e ONS não publicam contrato de API versionado. Layout muda entre períodos, e isso é normal.

Schema declarado, não inferido

Cada fonte tem um modelo Pydantic com schema_versao. Registro que não valida é descartado e contado, nunca carregado torto. Mudança de layout aparece como pico de inválidos no painel, não como número errado num relatório meses depois.

Raw antes do parsing

O payload cru vai para o Cloud Storage antes de qualquer interpretação. Bug de parser se corrige com reprocessar-raw, sem bater de novo na origem — importante para fonte com rate limit ou retenção curta.

Janela sempre explícita

Nenhum conector decide "hoje" sozinho. A janela de datas é parâmetro, e reprocessar é passar outra janela. As janelas de agendamento são largas de propósito (30 dias no ONS, 90 no IBGE) porque essas fontes revisam dado publicado.

Layout canônico do raw no Cloud Storage

gs://<projeto>-raw/{fonte}/{entidade}/dt={AAAA-MM-DD}/{ingestao_id}.json.gz

# bucket com versioning, acesso público bloqueado, UBLA
# lifecycle: 90 dias → Nearline
# teto de 100 MB comprimido, conferido pelos metadados antes do download
Pergunta ao Google: para as fontes de arquivo (ONS CSV anual, InfoMercado, planilhas), vale manter esse padrão de raw imutável + carga, ou o desenho melhora com tabela externa / BigLake sobre o bucket e transformação só no BigQuery? Nosso viés foi carregar, para ter partição, clustering e custo previsível.

ness.06 · Origem

O CASO DIFÍCIL

CCEE: a origem que responde 403

A câmara de comercialização é a fonte mais importante do domínio — e a única que recusa acesso programático.

  • O sintoma: www.ccee.org.br e dadosabertos.ccee.org.br devolvem HTTP 403 a requisição automatizada. O TLS conecta; o bloqueio vem do servidor, com página de proteção. Atinge a API CKAN, a página do InfoMercado e o portal de dados abertos — inclusive a documentação.
  • O efeito colateral que importa: agente_ccee é uma das cinco dimensões comuns da Silver e hoje é a única sem fonte definida. Sem ela, cruzar dado interno com contabilização de mercado fica manual.
  • O que não fazemos: contornar proteção anti-bot. Acesso a dado de terceiro se resolve por via oficial, não por evasão.
ViaO que exigeEfeito no desenho
a. IP liberadoA Alup pedir à CCEE a liberação do IP de saída do ambiente GCPConector fica igual aos outros. Preferida — e pede IP de saída estável (NAT)
b. Credencial de agenteÁrea credenciada da Alup, que já é agenteAproxima a fonte da Onda 2; contrato de dados desconhecido
c. SQL Server do BalançoLer o realizado que a Alup já recebe e armazenaNão depende da CCEE. Pede driver SQL Server no framework

Pergunta ao Google: existe padrão de referência para ingestão de portal público que bloqueia automação — saída por NAT com IP fixo e reputação, algum caminho de acordo institucional, ou a recomendação é simplesmente tratar como fonte semi-manual e investir no contrato de dados com a origem?

INGESTÃO

O que é do framework e o que é da fonte

Um conector novo implementa duas funções. As outras nove etapas são do runner, iguais para as 13 fontes.

Particiona a janelaRespeita o limite da fonte (max_dias_por_requisicao) sem o conector saber disso.
extrair() — da fonteFala HTTP, driver de banco ou arquivo. É a única parte que conhece a origem.
Grava o raw no GCSJSONL gzip, antes de qualquer parsing. Habilita o replay.
transformar() — da fonteRenomeia campo, normaliza número BR, achata payload aninhado.
Valida com PydanticRegistro inválido é descartado e contado; o valor rejeitado não entra no log.
Acrescenta colunas técnicas_ingestao_id, _ingestao_timestamp, _fonte, _schema_versao.
Carrega no BronzeLoad job com WRITE_APPEND e adição de campo permitida.
Registra a execuçãoUma linha em bronze._execucoes. Falha em registrar é falha, não detalhe.
Sanitiza o erroDSN, Bearer e parâmetro sensível são removidos antes de logar ou persistir.

class OnsCarga(Conector):

    schema = RegistroCarga

    def extrair(self, janela) -> Iterator[dict]:
        # fala com a origem, devolve dicionários brutos

    def transformar(self, bruto) -> dict:
        # ajusta o registro ao schema
A prova de que o desenho aguenta: as quatro fontes concluídas exercitam formatos deliberadamente diferentes — JSON diário, JSON aninhado mensal, cadastro paginado de 25 mil linhas e CSV anual remoto. O framework absorveu as quatro sem alteração; só extrair() e transformar() mudaram. Na Onda 3, extrair() passa a falar com driver de banco e o contrato continua o mesmo.

ness.09 · Tratamento

CAMADAS

Uma regra por camada, sem exceção

Raw
Cloud Storage. Objeto imutável, o que a fonte devolveu, gravado antes do parsing. Só isso.
Bronze
Tabela append-only. Fiel à origem, sem regra de negócio. Particionada por data de ingestão, clusterizada pelas chaves de consulta.
Silver
View. Tipagem, unidade, deduplicação por QUALIFY ROW_NUMBER() e as cinco dimensões comuns.
Gold
View. Uma pergunta de negócio nomeada por view. Teste de CI exige que só leia da Silver.

Bronze — sem partição o custo é do cliente

CREATE TABLE IF NOT EXISTS
  `${projeto}.bronze.ons_carga` (
  data_referencia DATE NOT NULL,
  submercado      STRING NOT NULL,
  carga_mwmed     NUMERIC NOT NULL,
  _ingestao_id, _ingestao_timestamp,
  _fonte, _schema_versao
)
PARTITION BY DATE(_ingestao_timestamp)
CLUSTER BY data_referencia, submercado;

Silver — a dedup vive aqui

CREATE OR REPLACE VIEW
  `${projeto}.silver.ons_carga` AS
SELECT data_referencia, submercado,
       carga_mwmed, ...
FROM `${projeto}.bronze.ons_carga`
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY data_referencia, submercado
  ORDER BY _ingestao_timestamp DESC
) = 1;

-- a ingestão mais recente vence:
-- o ONS revisa o que publicou

Gold — responde uma pergunta

CREATE OR REPLACE VIEW
  `${projeto}.gold.carga_mensal_submercado` AS
SELECT periodo_apuracao, submercado,
  AVG(carga_mwmed) AS carga_media_mwmed,
  MAX(carga_mwmed) AS carga_maxima_mwmed,
  MIN(carga_mwmed) AS carga_minima_mwmed
FROM `${projeto}.silver.ons_carga`
GROUP BY periodo_apuracao, submercado;

DIMENSÕES COMUNS

Cinco colunas que tornam o cruzamento possível

Toda view Silver expõe as mesmas cinco dimensões — inclusive como NULL, quando a granularidade da fonte não as tem.

DimensãoDonaSituação

  • Dimensão tem dona nomeada. Uma fonte é a autoridade de cada dimensão; as outras se conformam a ela. Sem isso, duas fontes divergem no código da usina e ninguém sabe qual está certa.
  • NULL declarado é melhor que coluna ausente. A carga do ONS é agregada por subsistema, então codigo_usina e agente_ccee saem como NULL com comentário — e o cruzamento não quebra.
  • Retificação é questão aberta de negócio, não técnica: quando a CCEE recontabiliza um mês fechado, sobrescreve-se ou versiona-se? Está no questionário enviado ao cliente, e a resposta muda o desenho da Silver.
Pergunta ao Google: conformar dimensão dentro de cada view Silver escala até 13 fontes, ou vale um conjunto de dimensões conformadas próprio (tabelas de dimensão versionadas, com SCD tipo 2 para usina que troca de coligada)?

ness.11 · Tratamento

TRANSFORMAÇÃO

SQL versionado, sem framework de transformação

  • O que é: arquivos .sql em sql/{bronze,silver,gold}/, aplicados por um deploy idempotente — CREATE TABLE IF NOT EXISTS no Bronze, CREATE OR REPLACE VIEW nas demais. Sem dbt e sem Dataform na Fase 1.
  • Por quê: o contrato não pede; o handoff ao time do cliente fica com uma peça a menos para operar; e o volume da Fase 1 é de views, não de um grafo com centenas de modelos. Tudo é legível por quem sabe SQL, sem ferramenta intermediária.
  • O custo que assumimos, por escrito: teste de dado e linhagem automática — que uma ferramenta daria de graça — ficam por nossa conta. A linhagem é o componente 07 (dicionário de dados, um por fonte) e o Dataplex entra na Onda 4.
  • O que o CI garante hoje: teste que exige que toda view Gold leia da Silver, com exceção estreita e nomeada para as views de sistema (_execucoes e INFORMATION_SCHEMA).
A cláusula de saída está escrita: se o número de views crescer muito além do previsto, reavaliar a decisão vira um ADR novo — não um remendo. É exatamente o tipo de gatilho que gostaríamos de calibrar com quem já viu isso dar errado.
Pergunta ao Google: Dataform é nativo do BigQuery e não cobra ambiente ligado — o argumento de custo que vale contra o Composer não vale contra ele. A pergunta é de handoff e de peso operacional: em um projeto de ~15 views que será operado por um time pequeno, Dataform paga o próprio custo de aprendizado pelos testes de dado e pela linhagem que traz? E qual é o caminho de migração de SQL solto para Dataform depois, se a Fase 2 crescer?

bronze._execucoes — o log que é também evidência de homologação

Falha ao registrar é falha. Se a carga funciona mas o registro operacional não é gravado, a execução não pode ser declarada sucesso — e não pode ser homologada. O erro é propagado de propósito.
  • Log estruturado com correlação por ingestao_id, alimentando Cloud Logging e Error Reporting. Toda linha de log de uma execução é filtrável por um único identificador.
  • Três alertas em Terraform: falha de ingestão, silêncio (a fonte deixou de reportar) e inválidos em alta. O terceiro é o que pega mudança de layout na origem antes de o número aparecer errado.
  • Painel de saúde por fonte — frescor, confiabilidade e volumetria — sobre a view saude_ingestao. Monitoramento, não BI.
  • Replay auditável: reprocessar do raw grava uma execução nova com modo=REPLAY e ponteiro para a execução original. O histórico não é reescrito.
  • Idempotência é teste: carregar a mesma janela duas vezes é caso de teste em cada fonte. Bronze duplica de propósito; a Silver é quem resolve.
Pergunta ao Google: vale trocar esse log próprio por Dataplex data quality / data profiling, ou os dois convivem — um para "a carga rodou", outro para "o dado faz sentido"?

ness.14 · Operação

CUSTO

A conta é do cliente — e a janela para acertar é agora

Custo já gasto não se rateia depois. O rateio se apoia em rótulo aplicado no momento do consumo.

Rotular antes do primeiro apply

Datasets, bucket, jobs e secrets já carregam projeto, ambiente e camada. Recurso sem rótulo entra na fatura como massa indistinta, e nenhum relatório recupera isso retroativamente. Como o ambiente ainda não existe, estamos no único momento em que isso sai de graça.

Particionar e clusterizar sempre

É regra do projeto, não otimização posterior: toda tabela Bronze é particionada por data de ingestão e clusterizada pelas chaves de consulta. Sem isso, o custo cresce por varredura completa.

Medir o próprio gasto

Uma view Gold sobre INFORMATION_SCHEMA.JOBS e TABLE_STORAGE responde "quanto o lake custou, em quê, e o que mudou". Mais um orçamento com alerta, em Terraform. Retenção do raw: 90 dias até Nearline.

Uma exceção honesta ao nosso próprio processo: a regra do projeto é "recurso GCP que não está no Terraform não existe". O billing export parece ser configuração da conta de faturamento, sem recurso Terraform equivalente. Se confirmado, vira passo manual de runbook com dono nomeado — exceção documentada, não furo descoberto em produção. Gostaríamos de confirmar isso com vocês.
Perguntas ao Google: (1) o volume da Fase 1 é modesto, mas se a granularidade do ONS virar semi-horária com histórico longo, o volume muda de ordem — em que ponto sai de on-demand para slots/edition? (2) faz sentido partition expiration no Bronze, dado que o raw no GCS já é a memória longa? (3) o eixo de rótulo por fonte de dado é o certo para atribuir custo por conector, ou existe recorte melhor?

SEGURANÇA

Menor privilégio, por recurso

  • Credencial só no Secret Manager, concedida por secret, nunca no projeto inteiro. Nada em código, .env versionado, fixture, log ou mensagem de erro — nem "temporariamente".
  • Uma service account de ingestão, com um único papel no nível do projeto (bigquery.jobUser, que é inevitável para criar job). Editar dado é permissão do dataset Bronze; o bucket dá criar e ler objeto, sem administrar bucket; invocar Cloud Run é concedido por job.
  • Deploy por Workload Identity Federation — o CI não guarda chave de service account.
  • Erro sanitizado antes de sair: DSN, Bearer e parâmetro sensível são removidos antes de logar ou persistir. Erro de validação não carrega o valor rejeitado.
  • Banco interno com credencial read-only na origem e DSN única no Secret Manager, com driver puro-Python — sem cliente nativo para instalar no container.

ness.16 · Situação

ESTADO REAL

O que está provado e o que não está

Provado

  • Framework de ingestão completo: janela, raw no GCS, validação, colunas técnicas, carga, log — 226 testes, 92% de cobertura.
  • Quatro fontes públicas verificadas contra as APIs reais em dry-run, incluindo 25.263 registros da ANEEL com zero inválidos em 28 segundos.
  • Terraform completo: datasets, bucket, secrets, Cloud Run Job, Scheduler, IAM por recurso, alertas e orçamento — fmt e validate limpos.
  • CI/CD com seis portões verdes; deploy de views idempotente; replay do raw; caminho de banco relacional pronto para a Onda 3.

Não provado — e é aqui que aparecem os erros que teste local não pega

  • Nenhuma linha chegou a um BigQuery real. O projeto GCP do cliente ainda não foi provisionado.
  • Primeiro terraform apply, primeira imagem publicada e primeira carga ponta a ponta: pendentes. É onde surgem IAM insuficiente, cota de API, permissão de bucket e formato que o BigQuery recusa.
  • Replay contra objeto real no GCS e linhagem conferida no BigQuery: pendentes.
  • Cinco fontes com credencial ou VPN pendente; a CCEE bloqueada por 403.
Por isso esta sessão é agora. Crítica que chega antes do primeiro apply é reprojeto de graça. Depois da Onda 2, é migração.

A PAUTA

Oito perguntas que valem mais que uma aprovação

01
Ingestão Conector Python em Cloud Run é o padrão certo para 13 fontes heterogêneas de baixo volume, ou há serviço gerenciado que reduz código sem aumentar acoplamento?
02
Bancos internos Datastream com CDC ou extração por janela via driver? A operação do cliente tem janela restrita — isso muda a resposta?
03
Orquestração Cloud Workflows como degrau entre Scheduler e Composer, ou é um passo intermediário que só adiciona uma peça?
04
Transformação SQL versionado ou Dataform? O que muda no handoff a um time pequeno, e qual o caminho de migração depois?
05
Camadas Bronze append-only com dedup na view Silver: aguenta 13 fontes, ou o ponto de virada para materializar chega antes do que pensamos?
06
Custo Taxonomia de rótulo, partição, retenção do raw e o ponto de saída de on-demand para slots — o que faríamos diferente antes do primeiro apply?
07
Governança Dataplex na Onda 4 é tarde? Catálogo, linhagem e qualidade deveriam entrar junto com a primeira fonte?
08
Origem bloqueada Existe padrão de referência para portal público que recusa automação — IP de saída estável, acordo institucional, ou aceitar a via semi-manual?
O que pedimos concretamente: para cada pergunta, o nome do serviço que você usaria, o trade-off que aceitaria e — se houver — o caso em que viu essa escolha dar errado. Vamos registrar as respostas como decisões de arquitetura no repositório, com a devida atribuição.

PRÓXIMOS PASSOS

O que acontece depois desta sessão

RegistrarCada recomendação vira ADR novo ou revisão de ADR existente, com o argumento que a motivou.
Reprojetar o que couberAntes do primeiro terraform apply. É a janela em que mudar de desenho não custa migração.
AplicarPrimeiro apply com a taxonomia de custo já definida, primeira carga ponta a ponta, três dias consecutivos de sucesso.
VoltarRevisão nova quando a Onda 3 abrir os sistemas internos — é onde o desenho encontra o dado difícil.
Uma última nota sobre método. Toda decisão estrutural deste projeto está escrita como ADR, com contexto, decisão e consequência assumida. Não pedimos que você concorde com as oito decisões — pedimos que aponte quais delas você desfaria, para que a consequência deixe de ser assumida e passe a ser corrigida.
